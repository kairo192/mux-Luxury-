# Mus Luxury (LUXE) — POS Offline Durability & Hardware Architecture

**Application:** Windows Desktop CMS & POS (`apps/desktop-cms/`)  
**Target OS:** Windows 10 / 11 64-bit  
**Framework:** Tauri 2 (Rust Core + React 18 / TypeScript WebView2)

---

## 1. Architectural Philosophy: Offline-First Reliability

Retail store environments in Algeria face frequent intermittent internet outages. The Mus Luxury POS is architected so that **the physical store never halts operations when the internet drops**.

A cashier must be able to:
1. Scan barcodes and look up products instantly without network lag (< 5 ms).
2. Ring sales with cash, card, or split tenders.
3. Open the cash drawer and print receipt slips offline.
4. Accumulate hundreds of transactions durably on disk.
5. Synchronize automatically and idempotently once internet connectivity resumes.

## 2. Local Catalog Mirror (`pos_mirror.sqlite3`)

### 2.1 Storage Location & Engine
The catalog mirror resides in `%APPDATA%/dz.musluxury.cms/pos_mirror.sqlite3`.
- Engine: Embedded SQLite via Rust `rusqlite` crate.
- Concurrency: WAL (`Write-Ahead Logging`) mode enabled (`PRAGMA journal_mode = WAL; PRAGMA synchronous = NORMAL;`). Lookups never block background synchronization writes.

### 2.2 Schema Definition
```sql
CREATE TABLE IF NOT EXISTS products (
    id                INTEGER PRIMARY KEY,
    sku               TEXT,
    name_fr           TEXT NOT NULL DEFAULT '',
    name_ar           TEXT NOT NULL DEFAULT '',
    name_en           TEXT NOT NULL DEFAULT '',
    selling_price_dzd INTEGER NOT NULL DEFAULT 0,
    purchase_cost_dzd INTEGER NOT NULL DEFAULT 0,
    main_image_url    TEXT,
    status            TEXT NOT NULL DEFAULT 'draft',
    category_id       INTEGER,
    updated_at        TEXT,
    deleted           INTEGER NOT NULL DEFAULT 0,
    name_normalized   TEXT NOT NULL DEFAULT ''
);
CREATE INDEX IF NOT EXISTS idx_products_name_norm ON products(name_normalized);
CREATE INDEX IF NOT EXISTS idx_products_sku ON products(sku);

CREATE TABLE IF NOT EXISTS variants (
    id                 INTEGER PRIMARY KEY,
    product_id         INTEGER NOT NULL,
    sku                TEXT,
    title              TEXT NOT NULL DEFAULT '',
    barcode            TEXT,
    price_override_dzd INTEGER,
    stock_qty          INTEGER NOT NULL DEFAULT 0,
    is_active          INTEGER NOT NULL DEFAULT 1,
    updated_at         TEXT,
    deleted            INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_variants_barcode ON variants(barcode);
CREATE INDEX IF NOT EXISTS idx_variants_sku ON variants(sku);
CREATE INDEX IF NOT EXISTS idx_variants_product ON variants(product_id);
```

### 2.3 Incremental Delta Synchronization
The desktop sync worker runs every 30 seconds when online:
1. **Initial Boot:** If mirror is empty, queries `GET /api/v1/admin/pos/catalog/snapshot` to download the entire catalog in a single gzipped payload.
2. **Periodic Delta:** Queries `GET /api/v1/admin/pos/catalog/deltas?since=<CURSOR_TIMESTAMP>`.
3. The response contains only rows modified or deleted since the cursor.
4. Rust applies the delta in an atomic transaction (`tx.commit()`) and updates the sync cursor.

## 3. Durable Offline Sales Queue (`offline_sales_queue`)

### 3.1 Migration from `localStorage` to SQLite
Previously, offline transactions were temporarily queued in browser `localStorage`. In this release, offline sales are stored in the local SQLite database.

```sql
CREATE TABLE IF NOT EXISTS offline_sales_queue (
    client_txn_id       TEXT PRIMARY KEY,
    item_type           TEXT NOT NULL DEFAULT 'sale',
    created_at          TEXT NOT NULL,
    register_session_id INTEGER,
    payload_json        TEXT NOT NULL,
    total_dzd           INTEGER NOT NULL DEFAULT 0,
    status              TEXT NOT NULL DEFAULT 'pending',
    error               TEXT,
    reason              TEXT,
    attempts            INTEGER NOT NULL DEFAULT 0,
    sale_reference      TEXT,
    updated_at          TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_offline_sales_queue_status ON offline_sales_queue(status);
```

### 3.2 Transaction States
- `pending`: Created offline; waiting for server synchronization.
- `synced`: Accepted by server; recorded in central inventory and treasury ledgers.
- `conflict`: Server rejected due to business rule (e.g. stock depleted); preserved for cashier review.
- `failed`: Transient error; eligible for automatic retry.

### 3.3 Idempotency Guarantee
Every transaction generated by the POS generates a unique UUID `client_txn_id` (e.g. `postxn-1731154000-a8f9`). When flushing the queue to `POST /api/v1/admin/pos/sync`:
- If the backend receives an identical `client_txn_id` multiple times, it returns the existing sale reference without creating duplicate orders or double-deducting stock.

## 4. Hardware Bridge Architecture

The Tauri application bridges Windows USB/Serial/HID hardware through native Rust threads:

```
+-------------------------------------------------------------+
|                 Windows Desktop POS Application             |
+-------------------------------------------------------------+
       |                        |                       |
       v                        v                       v
[ USB HID Barcode ]     [ ESC/POS Thermal ]     [ RJ11 Cash Drawer ]
Keyboard emulation      Raw Windows Spooler     Pulse via Printer Pin
Search-as-you-type      80mm paper cutter       `ESC p 0 25 250`
EAN-13 check digit      Logo + QR generation    Auto-kick on payment
```

### 4.1 ESC/POS Thermal Receipt Printer
- Communicates via Windows Spooler (`winspool.drv`) or direct COM/USB paths.
- Generates standard ESC/POS command sequences:
  - Text alignment and double-width luxury headers.
  - Itemized rows formatted in tabular French and Arabic text.
  - Partial cut command (`GS V 66 0`).

### 4.2 Cash Drawer Auto-Kick
- Connected via standard RJ11 connector to the receipt printer's DK port.
- Triggered automatically on Cash payment completion by sending drawer pulse:
  `\x1B\x70\x00\x19\xFA` (`ESC p 0 25 250`).

### 4.3 Barcode Scanner & Search
- Works as a standard HID keyboard device.
- POS listener hooks continuous keystrokes. When an Enter terminator is detected within 50 ms per character, the input is treated as a hardware scan and looks up the EAN-13 code in the local SQLite mirror instantly.
